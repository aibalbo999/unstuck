# 工作台讀取與重跑請求診斷（2026-10-23）

## 查得的原因與界線

`GET /api/watchlist/daily-dashboard` 會先等待全報告目前品質投影，再開始其餘彙整。指定 Mac 的四次原始日誌記錄品質子程序成功，但耗時 34.016、37.633、38.849、40.779 秒；舊子程序讀取期限為 25 秒，整體品質讀取為 30 秒，故完整成功結果尚未完成，端點已回 503。這是讀取期限與現有 201 份最新報告工作量不相容，不能把先前完成的投影當本次新結果。

本次將品質子程序上限調為 60 秒，含既有最多 20 秒準備程序的總上限為 85 秒。仍只有一個品質子程序；重疊相同請求共用進行中的工作，不新增佇列、不快取已完成結果、不修改品質規則或來源前後檢查。來源變更、規則漂移、失敗及超時仍回明確 unavailable/503。報告數增長或主機競爭使查核超過新上限，仍可能不可用；這次沒有宣稱改善計算演算法的速度。

瀏覽器工作台重疊 GET 改用既有 `requestJsonCoalesced`，只合併尚未完成的相同讀取。失敗也立即移除，下一次明確刷新會重新查核。工作台失敗時保留已取得的基本狀態，但明示「工作台查核未就緒／工作台讀取失敗」。

1623 的歷史請求是 `2026-10-23 06:37:10` 的本機 HTTP POST，隨後開啟該工作的結果串流。工作 `99075f7d7d1a42ad8fe56c3e682c3bda` 在 06:46:32 因 Agent 6 的 MAX_TOKENS／品質阻斷失敗，未發布。這組呼叫與預覽重跑流程相符，但既有日誌沒有操作來源標記，不能認定是某位使用者、UI 自動觸發、排程或攻擊。

隔離測試確實重現：預覽重跑／追蹤警示處理函式連續呼叫會送出兩次 POST。新增進行中防重；預覽同檔案只共用一個請求與串流，追蹤批次阻止重入，工作台依動作與目標阻止進行中的同一動作。完成或失敗後解除，保留合法的再次明確操作。伺服器原有 active-job attach 機制不變。這些改善不能證明歷史那一筆的成因。

## 日後查核

三個 UI 入口送出 `X-Stock-Agent-Action-Source`：`report_preview`、`decision_tracking`、`operator_summary`。伺服器只接受上述標記作為日誌欄位，其餘記為 `unspecified`；每次已接受的重跑回傳新的 `request_id`，並記錄 `report_rerun_request`、來源標記、檔名、scope、job ID、是否要求入列及是否復原孤兒佇列工作。此標記由呼叫端提供，可偽造，也不是身分認證或操作授權。舊呼叫端繼續可用。不得以這些欄位識別真實操作者；不記錄 token、完整標頭、referer、IP 或瀏覽紀錄。

## 驗證與部署界線

一般測試仍走 `tests/run_prompt_boundary_tests.py`，SQLite 隔離且無網路。UI fixtures 的 requestJson 是記憶體模擬；測試伺服器只綁 localhost，HTTP POST 一律 405，不能連正式重跑。完整品質 smoke 使用正式證據唯讀連線與禁止正式檔案寫入的 guard；以直接唯讀 artifact adapter 取代會建立 lock 的 storage，且不執行 index 同步或工作台其他 fanout。因此這是品質讀取驗證，不能宣稱已完成正式工作台端到端部署驗收。

固定批次 `hcs-legacy76-df03143a097e1e25` 的既有 journal、76 分母、135 版本與原始結果不參與修改；不新增處置、不重跑掃描、績效評分或補證。沒有 schema migration、排程或交易變更。

正式部署須另外批准。先核對本次七個既有執行檔的 before SHA 與全部差異，保留其他修改；若漂移，重解衝突與回歸。備份這七檔並保存回復雜湊。來源部署後必須讓 API 載入新 Python 模組；現行正式入口 `start_mac.command` 的受控重啟會暫停所屬 API、worker 與 Redis，須另核准，先確認無不能安全暫停的工作。無資料庫寫入或重 apply。重新載入後以 GET 驗證 health、ready、工作台 200／真實錯誤、前端快取新版本及固定 70+3+3=76／validated0；不送正式重跑 POST。若回復，還原七檔並按相同已批准流程重新載入，保留日誌及現有資料庫。

## 2026-10-26 追蹤 API 在後續讀取時超時

`GET /api/decision-tracking` 實際回傳 503／`tracking_read_timeout`。同一常駐服務的日誌顯示，追蹤子程序在回應超時之後仍成功完成，兩次後續讀取分別耗時 28.597、33.639 秒；原本只有首次讀取允許 35 秒，其後均限 20 秒，因此工作量未減少時會持續失敗。這次準備程序成功，並非資料庫連線或模型供應商失敗。

唯讀量測的追蹤範圍為 8 檔、32 份各模式報告；單次來源指紋約 3.56 秒。另以 cProfile 執行的完整品質投影約 33.97 秒，其中證據檢查約 18.87 秒；profiler 有額外開銷，不能把這組時間當作 API 延遲。報告逐項套用當前證據規則是主要工作量，本次未改變其演算法或判定。

首次正式重載後，自動開啟網站的真實並行載入測得 cold 子程序成功耗時 56.877 秒，仍超過初修的 45 秒；瀏覽器先回 503，較晚加入同一進行中工作的請求則成功回 200。後續 warm 子程序耗時 40.304 秒。這個差異證明單獨唯讀量測不能取代真正網站啟動驗收，初修來源與完整日誌另存 `attempt-45s/`。

最終追蹤投影對後續讀取允許 60 秒，新子程序的冷啟動允許 75 秒，總請求允許 100 秒，涵蓋既有最多 20 秒準備及 75 秒冷啟動投影。超過期限、來源變更與規則漂移仍明確不可用；重疊相同請求共用進行中的單一工作，完成結果不快取。全報告品質查核的獨立通道與既有期限不在本次修改範圍。

縮時回歸先確認兩種失敗：成功完成首次讀取後，模擬 34 秒的後續查核會在原 20 秒限制下回 unavailable；模擬 57 秒冷啟動也會超過初修的 45 秒。修正後應取得完整目前結果，重疊請求只執行一次，下一次不同版本重新計算。正式服務重載、最終隔離回歸及 HTTP 驗收的結果另保存於 `/Volumes/X10 Pro Mac/stock-agent-archives/tracking-api-503-20261026/`。
